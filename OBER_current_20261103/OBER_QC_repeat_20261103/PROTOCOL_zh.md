# 兩個全新QC輪次：不重用舊QC回應

## 精確範圍

使用最新OBER_rule_QC_20261103已凍結的規則、來源、提示詞、schema、gpt-5.6-luna、medium、max_output_tokens=4500與k2。58篇中1篇固定規則接受、57篇需QC。每個輪次重新對57篇各呼叫兩次模型，形成一組QC共識；A、B共228個新的預定QC呼叫，不把上次那一對回應再當兩輪。

此實驗只測QC共識這一層的操作變動。G/T病例審查、病例事實、原正式97筆、上游候選與文獻檢索固定；不是從原始病歷重新執行全部OBER，也不涵蓋PubMed檢索變化。49例87個答案配對仍留在分母，Candida不同species不合併。5個可能因文章閘門變動的候選範圍不變。

A1六個病例匹配欄位作共同控制，原來已有的固定A1回應明確重用，不偽稱本輪新呼叫。若任一新QC輪次使原來未做A1的候選開啟，按原A1 prompt補抽一次固定的r0/r1配對，供兩輪共同使用，以免臨時不同病例匹配混入QC效應；最多28個新病例匹配呼叫。這部分另記用量，不是QC重複的一部分。

## 新呼叫與可比性證明

- A、B用不同全新輸出目錄，只複製來源、routing、input與schema，絕不複製QC result/raw_response。
- 每個對應QC slot的初始API request body必須完全相同，且與原版請求一致；不得加入不同的round ID、時間戳或新指示到模型輸入。
- A與B的Response ID必須互不重複，並與舊QC版本互斥。保留實際request、response、時間、model、usage、fingerprint（若有）。
- 平台prompt cache可能仍命中，它不等於本地重用模型答案；本實驗不新增任何輸出快取來製造一致。中途中斷可接續同一輪已成功呼叫，不額外抽成第三輪。
- 不換模型、不改temperature／seed／規則／門檻。只測目前配置的實際變動，不把較低溫或固定seed假設成絕對確定。
- 原格式／來源錯誤仍最多修補一次，所有修補計入用量；另列是否因此使最終選用請求不同。不為了支持或F1重抽。

## 比較層級

1. 單次模型輸出：兩輪同slot的原始JSON是否不同、決策相關signature是否不同。
2. 各輪內：兩次QC分歧篇數、未解QC篇數。
3. 跨輪共識：接受／QC狀態翻轉、兩輪都接受但分類不同、文獻資格／支持型別變動；雙方都留QC不冒稱醫學語義已相同。
4. 病例：S、G/T A1篇數、待查來源、k2補入清單是否相同。
5. 評分：precision／recall／F1及TP／FP／FN；完整k0…10對照也保留，但主k2不換。F1相同不等於病原清單相同，所以同時比集合。

只採兩個預定輪次，不挑選較好輪次當主結果，不依答案改QC定義。兩輪全部無答案選擇凍結後，才讀參考答案計分；歷史答案早已用於開發，仍不是獨立test。

## 解讀

若相同配置出現分類差異，就是本次觀察到的非確定性；不假稱已完全排除後端版本差異。若最終清單與F1相同，只能說本次兩輪未改變門檻後結果，不表示文章判讀無變動或未來一定相同。樣本只有兩輪，不足估算可靠的長期穩定機率，更不是醫學正確性驗證。

方法依[OpenAI Docs evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)分開比較模塊與中間輸出，而非只看總分。這不使用OpenAI Evals平台，不上傳答案資料集。
